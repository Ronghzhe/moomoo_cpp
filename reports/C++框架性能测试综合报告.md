## 2. 范围与方法



### 2.1 范围


| 编号  | 名称        | 起点                       | 终点               |
| --- | --------- | ------------------------ | ---------------- |
| 1   | 执行延时      | Executor 认领可执行任务         | 策略进程本 leg 结束     |
| 2   | 调度延时      | 任务入库                     | Executor 认领      |
| 3   | 行情延时      | BasicQot / OrderBook 订阅  | 首条及后续 push；档位时间差 |
| 4   | Python 调用 | 公式求值 / Telegram 发送       | 调用返回             |
| 5   | API 包装    | 裸 SDK place/query/cancel | OrderClient 对应封装 |
| 6   | 稳定性       | 连续模拟盘循环                  | 失败率、延时漂移、内存      |




### 2.2 方法学

1. 时间单位：毫秒；微秒字段按 ÷1000 换算后入表。
2. 执行延时主表（第 4 节）为**合并样本**：基线 `20260827_030418`（开平各 6）+ 今日较好批次 `20260902_062341`（开平各 50）。今日另一批 `065439` 因并行启动导致 OpenD 连接被挤（中位 ~890 ms），不并入第 4 节，仅留第 10 节对照。
3. 合并统计：剔除负延时后，各段再去掉最小/最大各 1 条；以 CSV 时间戳差分重算为准，自动 md 派生字段不采用。基线 `place_api_ms` 在合理范围（<1000）时按 SDK 耗时并入；基线 exit 的 SDK 采用附录 A 已发布值。基线 CSV 中部分 exit 发单/成交时间戳残缺，故「触发→报单」（exit）与「报单→成交」（开平）以 `062341` 为主。
4. 调度延时（第 5 节）按批次给全统计（n/中位/p90/均值/最小/最大）；claim 段排除负延时与缺 `executor_claim_ms`（附录 B）。
5. 基线调度段剔除负延时，以及缺少 `executor_claim_ms` 的样本。执行「去等待」见 4.4。
6. 「策略启动→触发」各子段由已有时间戳相邻差分得到（`shell_start` / `strategy_main_start` / `config_loaded` / `opend_connected` / `subscribe_done` / `order_client_ready` / `first_book_push` / `first_judge` / `entry|exit_judge_hit`），非新打点。

| query raw / wrapped        | 10  | 7.4 / 23.3  | 封装多一层 list 查询            |

明细：`reports/api_wrapper_latency_*.md`。旧表 place 100+ 易误导，结论应以 **C++ ~40–50 ms** 为准。

### 本节结论

1. **报单本身 ~40–50 ms**（C++），不是 100+。
2. Python 包装相对裸调用无显著额外成本；query 封装略慢但仍远小于报单。
3. Test 5 旧 place 数字保留仅作「Python 封装开销」参考，不代表 C++ 下单延时。
